# City Run base / city generation

Read GENERATE-CITY.md and public/city.json before generating a city. Keep all city-specific names, coordinates, club branding, required landmarks and limits in city.json or imported data; do not hardcode them in src/ or server/.
Create a separate repository for each requested city. Never overwrite the Eindhoven source repository or an existing city. Validate the geographic boundary against real OSM roads, rivers and railway geometry; a screenshot is supporting evidence, not a source of exact coordinates.
Use scripts/import-city.mjs for OSM data. All imported roads must be clipped and split at shared junctions. Rivers are polygons/lines, never arbitrary filled open polylines. Bridge decks are driveable across water and end at the configured boundary. Named historic/tourism/public landmarks must remain in data and visible/searchable in the full city map [G]. Do not fabricate missing landmark geometry or claim a complete real-world landmark inventory when OSM is incomplete.
Run npm test, npm run validate:city and npm run build. Test bridge crossing, boundary collision, city-independent branding and shared client/server geometry. Use a browser for a visual check. Cite OSM contributors and retain data provenance. A base with configured:false must show a clear setup screen, not a broken game.
Do not deploy or buy hosting unless the user authorizes it. Publish a new repo only within the requested repository scope. The generic engine must continue to pass the original Eindhoven regression tests stored under test/fixtures/eindhoven.
